# Rules rationale — evidence behind specific rules

Maintainer-only notes. The installer does not ship `tools/`, so nothing here reaches an agent's
context. Rules state the obligation and, where it helps compliance, a one-clause consequence;
the measurements and incidents that motivated a rule live here instead of being re-read on every
load. When a rule changes, update or drop its entry.

| Rule (owner) | Observation that motivated it |
|---|---|
| Argument names come from the operation skill; schema fetch at most once per tool per session (`content/rules/mcp-policy.md → C. Call discipline and server answers`, item 4) | In the analysed sessions 20 of 60 MCP calls were schema lookups that changed nothing. |
| Schema and project lookups are not repeated per call (`content/skills/mcp-1c-tools/docs/1c-graph-metadata-mcp.md`, *Schema lookups are not free*) | The analysed sessions spent a third of all calls on schema and project lookups that returned nothing new. |
| A lane closed by the server stays closed (`content/rules/mcp-first-search.md → Hard rule`, item 3) | The analysed sessions spent ten graph calls each proving one `tabular_part_columns_not_indexed` / missing-index warning through sibling tools. |
| Memory queries are one topic per query (`content/rules/project-memory.md → Provider routing`) | The merged query `working conditions benchmark conventions НачислениеЗарплаты Премия …` returned vacation-calendar notes in every analysed session. |
| Memory-only entry point (`project-memory.md` + `tool-policy.md`) | On 2026-10-06, source c1fb8e6 required 8,187 o200k_base tokens in policy/router/template/memory prerequisites before ordinary recall. The separate route requires about 2,000, preserving provider policy, scoped raw recall, same-turn correction capture and ambiguous-write handling. Counts exclude tool results and host instructions; this tokenizer is a reproducible proxy, not runtime billing. |
| Quick-fix closes on `verification-policy.md → Quick-fix gate` alone (`AGENTS.md → Triage`, `tools/validate-rules.ps1` `$quickFixFiles`) | On 2026-11-11, source 7f64ea1, the files `AGENTS.md` triggers named for a quick-fix BSL edit summed to 107,858 bytes against 121,221 for a full-cycle change: gates, delivery and playbooks (42 KB) were loaded for a change that runs two validators. After the change the quick-fix set is 58,613 bytes; the full-cycle set grew to 124,150 because the tool-key table, the helper-reuse rule and the artifact-free DoD moved into it. |
| `.dev.env` is read by key lines (`AGENTS.md → Project info`, `dev-standards-env.md §1`) | On 2026-11-11 the template rendered into every project held 20,731 bytes, of which 19,487 were comments and 1,190 the 66 `KEY=value` lines; every session and every subagent that reads settings paid for the comments. |
| Profile by self-knowledge; `AGENT_MODEL` is the fallback and the off switch (`model-adaptation.md → Selecting the profile`) | Before 2026-11-11 `AGENTS.md` and the router said an empty value means no profile, while the `Load` line of all five profiles said to load when the agent knows its model; empty is the installed default, so behaviour depended on which sentence a model weighed. The router's own trigger also loaded its 12.4 KB at the start of every configured session. |
| OpenSpec rules are split by phase (`sdd-integrations.md`, `sdd-propose.md`, `sdd-apply.md`) | The single 31,971-byte file was pulled into every subagent run because the installer always scaffolds `openspec/` and the trigger was "the project has an `openspec/` workspace"; it also held the only Definition of Done text and the helper-reuse rule, which non-OpenSpec work needs. With the 6.5 KB router, apply now loads about 18 KB and propose about 22 KB; a non-OpenSpec full-cycle change loads none of them. |
| Synchronization contract in its own file (`config-sync-contract.md`) | On 2026-11-12, source f23f98f, `/update1cbase`, `/loadfrom1cbase`, `/deploy-and-test` and `db-manage.md` sent the agent to `getconfigfiles.md` (13,659 bytes) for its 7 KB contract; the rest is the selected-object export procedure they never run. The contract read is now 7,668 bytes. |
| Monthly `/checkupdates` contract lives in the command (`checkupdates.md → Proactive run`) | On 2026-11-12 the monthly check loaded `support-feedback.md` (15,135 bytes, the only Russian-prose rule) for its 2.8 KB §4 and then the command (8,448), which pointed back. Now 9,760 bytes; `support-feedback.md` is 6,112 bytes of English, with ticket fields and scrubbing left to `/support`. |
| Total description ceilings (`tools/validate-rules.ps1` `*DescriptionTotalMaxBytes`) | Per-file ceilings let the listings hosts show in every session grow one file at a time; rule descriptions reached 11,098 bytes. Shortening the five model-profile descriptions brought them to about 10.8 KB; the totals are ratcheted just above the current values. |
| Operation-specific references in QA, binary and metadata skills | The 2026-10-06 split reduced entry files from 4,784 / 4,313 / 3,957 to 2,295 / 1,270 / 2,105 o200k_base tokens. Detailed contracts remain mandatory on their operation's trigger; a task requiring all references still pays for them. |
| One delegation criterion for metadata work (`1c-metadata-manage/SKILL.md → Dispatch Strategy`, `subagents.md` catalog row) | Before 2026-11-17 the skill delegated every create, every multi-step run and every task with a large domain doc to read, which covers nearly every mutation, while `subagents.md → Delegation principle` delegates from two metadata objects and the Opus 5 / Fable 5 profiles lean to direct execution. Fable 5.2 applies such a list literally, so a single new catalog paid for a subagent's fresh context and rule loads. |
| Plan unit and the Gate 5 changed-file set (`SKILL.md → Plan unit`, `verification-gates.md → Gate 5`) | The tools write registrations the agent never names: `meta-compile` and `meta-remove` edit `Configuration.xml` and subsystem content, `form-add` the owner object. Gate 5 asked for "every modified XML file" without saying where the list comes from. The IngvarConsulting/unica review of 2026-11-17 (main f7db575) was the prompt: its `apply` returns the final effects of a plan before writing; here the dump's `git status` plays that role. |
| `METADATA_PREVIEW=auto` previews only a `-Force` re-compile (`edit-preview.md → When preview runs`) | The former second trigger, "a tool or operation this project has not run before", could not be observed: nothing records which operations a project ran. A DSL-generation preview diffs a whole new file, while its definition JSON is the readable plan. Unica's plan / execution-token protocol was weighed and not copied: our tools are vendored and a preview here really writes and restores (`edit-preview.md → Why a wrapper`). |
| Stored data before removing or narrowing (`meta-manage.md → Stored data — removing and narrowing`) | On 2026-11-17 `meta-manage.md` showed `remove-attribute` and a `type=` change as plain examples, and the `CONFUSION` trigger on metadata shape fires only on ambiguity — «удали реквизит» is unambiguous. ITS std534 (`its-v8std-534-hdoc`) prescribes the decision, the `Удалить` prefix and the later removal; Unica's `metadata-modeling` skill keeps the same stop rule. |
| Review findings are checked before they are applied (`verification-delivery.md → Soft gate C`, *Acting on findings*) | Until 2026-11-17 the rules said only "fix critical / major findings". `review_1c_code` and `1c-code-reviewer` are model output (`mcp-policy.md → B`), and the Opus 5 profile asks reviewers for every finding with its confidence, so a parent applying findings as given acts on the false ones too. Adapted from obra/superpowers `receiving-code-review`. |
| Intent before design (`sdd-propose.md → Intent before design`) | The bundled OpenSpec 1.13.1 explore skill already resolves outcome and scope one question at a time, but propose had only batched `CONFUSION` rounds, which presuppose a fixed intent. Adapted from obra/superpowers `brainstorming`. |
| Descriptions name the trigger and the topics, not the procedure (rule and skill frontmatter; `README.md`, description budgets) | obra/superpowers `writing-skills` reports that when a skill description summarised its workflow, the model followed the summary instead of reading the body. The risk is sharpest for routers whose body comes only through `standards()` and for the OpenSpec phase files. On 2026-11-17 the descriptions of 15 rules and 6 skills were rewritten; the effect was not measured. Agent and command descriptions were left: an agent's body is its system prompt, and a command's body loads on invocation. |
| A standard is not evidence of runtime behaviour (`mcp-policy.md → A.2`) | The nearest existing wording covered one case: a clean `vcvalidatequery` proves parsing only (`verification-gates.md → Gate 3a`). A diagnosis of event order or data visibility could still rest on a quoted standard alone. Adapted from the IngvarConsulting/unica `object-events` skill (main 2018a4b, 2026-11-18). No eval case measures it yet. |
